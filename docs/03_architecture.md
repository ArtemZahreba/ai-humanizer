# 3. Архітектура програмного забезпечення

## 3.1. Загальна структура
Застосунок має розділені рівні:
1. **Frontend** — HTML, CSS та JavaScript.
2. **Routes/API** — Flask Blueprints, перевірка запитів і формування відповідей.
3. **Services** — бізнес-логіка гуманізації, промптів, моделей та історії.
4. **Data access** — SQLAlchemy ORM і SQLite.
5. **External AI** — Hugging Face Inference Router.

## 3.2. Ініціалізація
`app.py` містить `create_app()`. Під час створення застосунку завантажується `Config`, створюється каталог `instance`, ініціалізується SQLAlchemy, реєструються Blueprints, виконуються `db.create_all()`, `seed_default_prompts()` та `seed_default_models()`. Окремий механізм міграцій у поточній реалізації не налаштований.

## 3.4. Сценарій гуманізації
1. Користувач вводить текст і вибирає модель та промпт.
2. JavaScript надсилає JSON до `/api/humanize`.
3. Route перевіряє JSON, `client_id`, текст, довжину, ID моделі та промпту, `max_tokens`.
4. `HumanizationService` отримує активну модель і доступний промпт.
5. Сервіс формує prompt із тексту промпту, правил формату та введеного тексту.
6. `HuggingFaceService` надсилає запит до Hugging Face Router.
7. Результат перевіряється на непорожнє значення.
8. `HistoryService` зберігає дані в SQLite.
9. API повертає JSON.
10. Frontend показує результат.

## 3.5. Основні сервіси
- `HumanizationService` — координує гуманізацію та збереження результату.
- `HuggingFaceService` — викликає зовнішній AI API й обробляє помилки SDK.
- `PromptService` — працює зі стандартними та власними промптами.
- `HistoryService` — зберігає та отримує історію.
- `ModelService` — отримує зареєстровані моделі.

## 3.6. Обробка помилок
Помилки валідації повертаються як HTTP 400, відсутні ресурси — 404, обмеження провайдера — 429, помилки провайдера — 502 або 503 залежно від типу. Непередбачена помилка гуманізації журналюється через Flask logger.
